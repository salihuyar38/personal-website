Making HPC Applications Elastic with DynRM and Process Sets

September 2026

Based on the paper Dynamic Resource Management in HPC Systems using Dynamic Processes with PSets by Dominik Huber et al.

Introduction

High-Performance Computing systems are designed to execute large and computationally demanding workloads across many processors and nodes. Traditionally, however, the resources assigned to an HPC job are mostly static.

A job receives a certain number of nodes or processes when it starts, and those resources usually remain assigned to the job until it finishes.

This model is simple, but it can also lead to inefficient resource usage. An application may require many resources during one phase of its execution and significantly fewer resources during another phase. Nevertheless, with static allocation, it continues occupying the same resources throughout its lifetime. 

Traditional allocation

Time ------------------------------------------------>

Job A:
16 nodes ---- 16 nodes ---- 16 nodes ---- 16 nodes

The actual computational demand of the application might instead look more like this: 

Actual demand

Time ------------------------------------------------>

8 nodes ---- 16 nodes ---- 4 nodes ---- 12 nodes

This is where Dynamic Resource Management, or DRM, becomes interesting.

This article is based on the paper Dynamic Resource Management in HPC Systems using Dynamic Processes with PSets by Dominik Huber et al. The goal of this blog post is to explain the main ideas, architecture, and results of the paper in a more accessible and practical way.

The paper investigates how resources assigned to HPC applications can be changed dynamically while those applications are already running.

What Is Dynamic Resource Management?

Dynamic Resource Management allows a running application to gain or release resources during execution.

Instead of keeping the same allocation for the entire runtime: 

Static allocation

Start                    Finish
  |                         |
  v                         v

8 nodes ----------------- 8 nodes

the resource allocation can change over time: 

Dynamic allocation

Start                             Finish
  |                                  |
  v                                  v

4 nodes -> 8 nodes -> 12 nodes -> 6 nodes

This means that an application can potentially grow when additional resources are available, shrink when resources are needed elsewhere, and adapt its resource usage to different phases of execution.

From a system perspective, this additional flexibility can improve resource utilization, job throughput, waiting times, and overall turnaround time.

Why Dynamic HPC Is Difficult

At first, dynamically adding a few resources to a running application sounds straightforward.

Suppose an MPI application initially runs with four processes:

Rank 1
Rank 2
Rank 3

Now imagine that the resource manager decides to provide two additional resources.

We would like the application to continue with: 

Rank 0
Rank 1
Rank 2
Rank 3
Rank 4
Rank 5

However, this immediately introduces several questions:

  • Who creates Rank 4 and Rank 5?
  • How does the MPI application discover the new processes?
  • How are MPI communicators updated?
  • What happens to data distributed between the existing ranks?
  • Who decides whether adding new processes is actually beneficial?

Dynamic resource management therefore affects several layers of the HPC software stack.

This cross-layer complexity is one of the main reasons why dynamic resource management has not yet become the standard resource model in production HPC systems.

Dynamic Processes with PSets

The approach used in the paper is called Dynamic Processes with PSets, or DPP.

A central abstraction in DPP is the Process Set, abbreviated as PSet.

A PSet represents a group of processes. 

PSet A

{
    Rank 0,
    Rank 1,
    Rank 2,
    Rank 3
}

Instead of modifying processes directly across every layer of the HPC software stack, the system can operate on these process sets.

Changes to a PSet are expressed through Process Set Operations, or PSetOps.

Growing a Process Set

PSet A
{0, 1, 2, 3}

      GROW
        |
        v

PSet B
{0, 1, 2, 3, 4, 5}

Shrinking a Process Set

PSet A
{0, 1, 2, 3}

     SHRINK
        |
        v

PSet B
{0, 1}

An important idea behind DPP is the separation between Dynamic Process Management on the application side and Dynamic Resource Allocation on the resource-manager side. 

Application side                  Resource-manager side

Dynamic Process                   Dynamic Resource
Management                        Allocation
       |                                |
       +--------- PSet / PSetOp --------+

The application can describe which process configurations it supports, while the resource manager can decide which actual resource allocation should be applied.

What Is DynRM?

One of the main components introduced in the paper is DynRM, the Dynamic Resource Manager.

DynRM is a modular, Python-based resource manager that follows the DPP design principles.

It is important to distinguish between the general concept of Dynamic Resource Management and the software component DynRM.

Dynamic Resource Management is the general idea of changing resource allocations while jobs are running. DynRM is a concrete software implementation designed to realize and experiment with these ideas.

DynRM internally represents the HPC system using three main graphs: 

              DynRM
                |
     +----------+----------+
     |          |          |
     v          v          v
 Task Graph   PSet Graph  Topology Graph

The Task Graph

The Task Graph, often written as Gtask, represents the tasks or jobs submitted by users. 

Task A -----> Task B -----> Task C

Vertices represent individual tasks, while edges can represent dependencies between them.

This makes it possible to represent not only independent jobs, but also complete workflows containing multiple dependent tasks.

The PSet Graph

The PSet Graph, written as Gpset, represents the processes used to execute tasks. 

Task A
   |
   v
PSet 1
{P0, P1, P2, P3}

Dynamic process changes are represented using PSet operations.

PSet 2
{P0, P1, P2, P3}

The PSet Graph is especially important because it connects the application's view of dynamic processes with the resource manager's view of physical resources.

The Topology Graph

The Topology Graph, written as Gtopo, represents the actual resources available in the HPC system.

The topology graph can contain system objects such as partitions, nodes, and CPU cores together with their containment relationships.

How DynRM Fits into the HPC Software Stack

DynRM does not work alone. The dynamic software stack described in the paper combines several important HPC components.

                 v

                 |
                 v
          MPI Application

Each component has a different responsibility.

DynRM

DynRM contains the resource-management and scheduling logic.

It reasons about questions such as:

  • Which jobs are currently running?
  • Which resources are available?
  • Which applications can grow or shrink?
  • Would changing a resource allocation improve system performance?

PRRTE

PRRTE provides runtime and process-management functionality.

Its responsibilities include launching processes, monitoring them, terminating them, and performing process changes when a PSet operation is executed.

OpenPMIx

PMIx provides communication mechanisms between the different layers.

In the software stack described in the paper, PMIx is used for communication between DynRM and PRRTE and also between PRRTE and the application processes.

Open MPI

Open MPI provides the MPI environment used by the application.

In this dynamic software stack, Open MPI is extended so that applications can work with Process Sets and PSet operations and adapt their communication structures when the set of processes changes.

DynRM's Modular Architecture

Another interesting aspect of DynRM is that it is designed to be modular.

The architecture allows different implementations of:

  • Topology modules
  • Submission modules
  • Policy modules
  • System modules
  • Model modules

For example, different policy modules can be used to experiment with different scheduling strategies, while different system modules can interact with process managers such as PRRTE or other runtime systems.

This makes DynRM useful not only as a resource manager, but also as an experimental platform for researching new dynamic scheduling approaches.

How Does DynRM Decide Who Gets More Resources?

Giving every available resource to one application would not necessarily improve the system.

Consider the following situation: 

Job A -> 8 nodes
Job B -> 2 nodes
Free  -> 2 nodes

Imagine that Job A scales poorly beyond four nodes while Job B scales very well.

Giving the two free nodes to Job A might provide almost no performance improvement. Giving them to Job B might significantly improve its runtime.

DynRM therefore uses performance models to estimate how applications benefit from different resource configurations. 

Current allocation
        |
        v
Estimate application performance
        |
        v
Consider possible resource changes
        |
        v
Evaluate alternatives
        |
        v
Choose a better allocation

The optimization strategy described in the paper is based on Discrete Steepest Ascent.

At a high level, the optimizer considers three kinds of actions:

  1. Removing resources from jobs when beneficial
  2. Assigning available resources to jobs
  3. Swapping resources between jobs

System Performance vs. Individual Job Performance

An especially interesting part of dynamic scheduling is that the best resource allocation for one individual application is not always the best allocation for the complete HPC system. 

Before

Job A -> 8 nodes
Job B -> 2 nodes


After

Job A -> 6 nodes
Job B -> 4 nodes

Job A might become slightly slower, while Job B might become significantly faster.

If this reduces waiting time, improves utilization, and shortens the overall makespan of the workload, then the redistribution can still be a good system-level decision.

Main idea: Optimizing an HPC system is not always the same as making every individual application run as fast as possible.

Does Dynamic Resource Management Actually Help?

The paper evaluates the complete dynamic software stack using up to 100 HPC nodes.

The experiments use both synthetic workloads and adapted real-world HPC applications, including:

  • PETSc
  • XBraid
  • LibPFASST
  • DMR-CG
  • DMR-Jacobi
  • DMR-Laplace

The researchers compare traditional static EasyBackfilling scheduling with dynamic scheduling strategies based on Discrete Steepest Ascent.

In crowded synthetic workload scenarios with 100% dynamic jobs, the dynamic scheduling strategy reduced makespan by up to 31% and average job turnaround time by up to 39%.

An important observation is that the runtime of some individual jobs can increase under dynamic scheduling.

This happens because the scheduler may give an application fewer resources in order to achieve better parallel efficiency and improve system-wide metrics.

Dynamic resource management is mainly a system-level optimization. A single job can sometimes run longer while the entire workload finishes earlier.

Dynamic Scheduling Is Not Always Better

Dynamic Resource Management is not a free performance improvement.

Changing resources during execution introduces additional overhead and complexity.

  • New processes may need to be created.
  • MPI communication structures must be updated.
  • Application data may need to be redistributed.
  • The scheduler itself requires computation.
  • Different software layers must communicate during reconfiguration.

Data redistribution is particularly important.

For example, suppose four MPI ranks initially own different parts of a distributed data set: 

Before

Rank 0 -> data 0-249
Rank 1 -> data 250-499
Rank 2 -> data 500-749
Rank 3 -> data 750-999

After growing to eight processes, the data might need to be redistributed: 

After

Rank 0 -> 0-124
Rank 1 -> 125-249
Rank 2 -> 250-374
Rank 3 -> 375-499
Rank 4 -> 500-624
Rank 5 -> 625-749
Rank 6 -> 750-874
Rank 7 -> 875-999

This redistribution can be expensive and strongly depends on the application.

The paper also shows that dynamic scheduling does not outperform static scheduling in every scenario. In some less crowded experiments, event-based scheduling introduced enough overhead to increase the overall makespan.

What I Learned

Before studying dynamic HPC systems, I mostly thought of resource management as something that happens before an application starts.

A user requests a certain amount of resources: 

4 nodes
32 cores per node
2 hours

The scheduler decides when those resources become available, starts the job, and the allocation remains fixed until the application finishes.

Dynamic Resource Management changes this model.

    |
    v

    +---- Grow

    +---- Shrink

Resource allocation becomes part of the runtime behavior of the application.

What I found especially interesting is that this problem cannot be solved by one component alone.

DynRM alone is not enough. MPI alone is not enough. PMIx alone is not enough. PRRTE alone is not enough.

Instead, dynamic execution requires cooperation across the whole software stack.

DPP provides common abstractions for this cooperation through Process Sets and Process Set Operations, while DynRM uses these abstractions to perform dynamic scheduling and resource-management decisions.

For me, this is what makes the work especially interesting. It is not simply about designing a new scheduler. It is about designing a software architecture that enables applications, runtimes, process managers, and resource managers to cooperate while an application is already running.

Conclusion

Traditional HPC resource management assumes that applications use a fixed amount of resources throughout their execution.

Dynamic Resource Management challenges this assumption by allowing applications to gain, release, and redistribute resources while they are running.

The paper Dynamic Resource Management in HPC Systems using Dynamic Processes with PSets presents a DPP-based software stack that integrates DynRM, PRRTE, OpenPMIx, Open MPI, and dynamically adaptable HPC applications.

DynRM models tasks, process sets, and physical resources using graphs and combines this representation with performance-aware scheduling to decide how resources should be distributed.

The experimental results demonstrate that dynamic scheduling can improve important system-wide metrics, particularly when the HPC system is heavily loaded.

At the same time, the work also demonstrates the challenges of dynamic HPC: process reconfiguration has overhead, applications must support changing process counts, data may need to be redistributed, and several layers of the software stack need to cooperate.

How can applications, runtimes, and resource managers cooperate so that an HPC system can adapt its resources while workloads are already running?

DynRM and Dynamic Processes with PSets provide one possible answer to this question.
